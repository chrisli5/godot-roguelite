# Project: Action Roguelite (Godot 4, GDScript)

Last synced with code commit: `ccadfe6`. Update this line whenever this file changes.

Auto-attack action roguelite (Vampire Survivors-style combat) with a Slay the Spire-style room map.
Engine: Godot 4.x. The code uses `@abstract` and typed Dictionaries, so assume 4.5 or newer.
Elemental infusions (Fire, Frost, Lightning, Wind, Earth) are socketed into ability slots and drive evolutions.

## Code style
- Tabs for indentation. Static typing everywhere (`var x: int`, typed arrays and dictionaries).
- One `class_name` per script. `##` doc comments on public methods.
- Data lives in Resources (`.tres`), not hard-coded constants. Tunable numbers are `@export`.
- Tags are an enum (`Tags.Type`), never strings.
- No new `print()` calls in hot paths (damage, stat recalculation, invalidation).

## Architecture rules (do not break these)
- **Component isolation.** Child components never hold references to sibling nodes. The parent wires them with signals and method parameters. Entity, Player and Ability are the mediators.
- **EventBus** (autoload) is the global signal hub. `EventBus.active_player_instance_id` is how systems find the player; call `instance_from_id()` on it.
- **Slots.** Slot 0 is the Character Core (player stats). Abilities occupy slots 1-4 (`AbilityContainer.MIN_SLOT` / `MAX_SLOT`).
- **Ability pipeline.** `AbilityData` selects: deployment anchor, geometry driver, optional payload driver, stats profile. The ability runs anchor -> spatial query -> geometry driver. Evolutions swap those strategy nodes via `execute_ability_evolution`.
- **Stats.** `StatsContainer` caches lazily with dirty flags. Call `get_final_stat_value(stat_type)` with ONE argument. Tags come from the container's own `TagComponent`, never from the caller.
- **Tags.** `TagComponent` compiles three layers: `base_tags` (replaced from `AbilityData.structural_tags` in `Ability.swap_runtime_strategies`; an empty list logs a warning and leaves the tags unchanged), infusion tags (rebuilt from the run ledger, never stored on the component), and refcounted temporary tags from status effects. `get_permanent_tags()` is base plus infusion tags; `get_active_tags()` adds temporary tags. Stat cards, statuses, bursts and draft eligibility use permanent tags only; damage payload tags use active tags.
- **Run ledger.** `RunLedgerComponent` (on the Player) is the single source of truth for upgrades. Aggregate with `get_modifier_totals(slot, tags, stat)`, which returns `Vector3(flat, percent, multiplicative)`. Do not create temporary modifier resources in hot paths. Slot-specific purchases (infusions, Overclock) are stored under the key `"<upgrade_id>::slot_<n>"` and win over the plain key. An infusion's level for (slot, element) is stored nowhere else: `get_infusion_level(slot, element)` and `get_infusion_levels(slot)` sum the slot-specific tiers of cards whose `UpgradeDefinition.category` is `INFUSION` (never the id prefix). `InfusionTrackerComponent` holds no levels; it reads the ledger through `configure_slot_context(slot, ledger)`. Build and parse slot keys only through `PurchaseKey.make` and `PurchaseKey.parse`; the stored key format is unchanged. `get_card_tier(def, slot, permanent_tags)` is the single answer to whether a card applies to a slot. `StatsContainer` invalidates stats by asking it, so it holds no scope rules of its own. Overclock is derived the same way: `is_overclocked(slot)`; no component stores it.
- **Shared payloads.** A `CombatPayload` is shared by every projectile in a volley. Duplicate it before any per-hit mutation. Status effect resources are templates: never mutate them, keep runtime state in a separate per-application object (`StatusEffectInstance`). Per-hit state (for example a pierce count) lives on the projectile, never on the payload.
- **Driver library.** Geometry drivers: projectile (Targeted = nearest enemy, Straight = player movement direction, MouseAim; all use the fan helper with `PROJECTILE_AMOUNT` and 15 degree spread), area (RadialPulse, LinearSweep, Fissure, ConvergingVortex, ChainLink), persistent (OrbitingRing). Trajectories (`MovementStrategy`): Vector (default), Homing, Boomerang, SineWave, Tornado. The only payload driver is `MissileHitPayload`, which just sets the trajectory scene. Every geometry ends in `HurtboxComponent.take_hit(payload)`, so statuses apply from any shape. An evolution may change family (projectile -> area).
- **Driver stats.** Each driver reads specific stats from the ability's profile, and a missing stat reads 0.0: no `PROJECTILE_AMOUNT` means no shots, no `DURATION` kills a projectile instantly, no `CHAIN_RADIUS` means no chain. `mutate_base_profile` replaces the whole profile, so every evolution's stats profile must carry every stat its drivers read, plus `BASE_DAMAGE`, `COOLDOWN`, `CRIT_*`, `DOT_DAMAGE`, `STATUS_DURATION` and `STATUS_RAMP_CAP`, plus `AOE_RADIUS` for projectile and orbit abilities (it is their hitbox radius; Task G). A modifier on a stat that is missing from the profile has no effect (the stat reads 0.0), which is why Arcane Bolt's profile needed `STATUS_RAMP_CAP: 0.0` before Fire's cap bonus reached Burn.
- **Crit.** Rolled once per cast in `generate_hit_payload` (decided, simplest). A fan or chain crits entirely or not at all. A crit cast may also scale the cast's DoT snapshot through `CRIT_DOT_SHARE` (0 = off); ticks never roll their own crit.
- **Impact bursts.** A burst is secondary area damage centered on an enemy that was just hit. It is not an ability (no slot, cooldown, anchor, stats profile or tags). Parts: `ImpactBurstDefinition` (a resource: `burst_id`, `trigger` ON_HIT or ON_CRIT, `shape`, `damage_fraction`, `per_enemy_bonus`, `per_enemy_bonus_cap`, `applies_statuses`, `required_target_tag`, optional `effect_scene`; a null `shape` makes an effect-only burst that just spawns its effect), `BurstShape` (abstract; `find_targets(origin, stats, space_state, exclude_instance_id)` only finds targets, and may return the same hurtbox twice) with `CircleBurstShape` (radius = `AOE_RADIUS * radius_multiplier`), and the static runner `ImpactBurst.run`, which owns every rule. A card carries a definition in `UpgradeDefinition.impact_burst_payload`. The ledger resolves definitions for a slot (same scope rules as statuses, deduplicated by `burst_id`), `generate_hit_payload` stores them on `CombatPayload.impact_bursts` at cast time, and `HurtboxComponent.take_hit` runs each matching one deferred (physics callbacks may not allow spatial queries). Rules: the origin is the hit enemy's position, copied at hit time; the primary target is excluded; the burst fires on every qualifying hit (no per-cast cap); damage is `final_damage * damage_fraction * (1 + min(per_enemy_bonus * targets_caught, per_enemy_bonus_cap))`, where `final_damage` already includes a crit; the burst never crits and never triggers another burst (`CombatPayload.is_burst`); it applies no status unless its definition sets `applies_statuses`, in which case it carries the cast's statuses and their snapshots. `required_target_tag` is checked against the primary target before the hit's own statuses apply. An effect scene that extends `BurstEffect` receives a copy of the cast's payload through `configure` before it enters the tree. New shapes must only find targets; damage and recursion rules stay in the runner. Level gating of burst cards is not built (GDD item 33). `ProjectileSpawnerComponent.projectile_impacted` is not used for this.

## Append-only enums
`Stat.Type`, `Tags.Type`, `UpgradeDefinition.PayloadType`, and any other enum referenced from `.tres` files are stored as integers. Add new entries at the END only. Never insert, reorder, or delete entries.

## Run persistence
Room scenes are freed on every transition, so run state lives in `RunSession.state` (a `RunState` resource).
- `Player._exit_tree` captures it (skipped if the player is dead). `Player._ready` restores it before `player_spawned` is emitted. `MapGenerator` resets it when a new run starts.
- Any NEW state that must survive rooms needs three edits: a field in `RunState`, capture in `Player.capture_run_state`, restore in `Player._restore_run_state`.
- Exception: `UpgradeManager` lives under the Systems node of the World scene (freed with it). It writes `RunState.pending_draft_levels` through to `RunSession.state` on every queue change and reloads it in `_ready`.
- Not persisted on purpose: status effects, temporary modifiers, cooldown timers, uncollected pickups, offer drafts (eligibility is derived from persisted state).

## Upgrade drafts, evolution and Overclock
- **Level-up drafts** never contain infusion cards, evolution cards or Overclock cards.
- **Infusion drafts** are separate from level-up drafts (`UpgradeManager.trigger_infusion_draft_event`). Only elements that at least one ability can accept are offered. When infusion drafts happen in a normal run is undecided; today it is triggered only from the debug panel (F1, Run tab). The infusion card in the pool is global. The per-element ceiling is enforced per ability by `InfusionTrackerComponent.is_element_socket_allowed`, not by the profile's `total_tiers`.
- **Offer drafts.** When an ability reaches its soft cap (`EvolutionGateComponent.is_offer_eligible`), `UpgradeManager` presents a forced draft for it: every evolution card that matches, then Overclock. No decline, no reroll, no random fill. Checked after each confirmed infusion and at room start, before queued level-ups. Never stored.
- **Evolution cards** are `ABILITY_UNLOCK` definitions with `evolves_from` (the ability's current `AbilityData`, compared by `resource_path`) and `recipe_requirements` (elements that must be at the soft cap).
- **Overclock** is a generic `ABILITY_OVERCLOCK` card, logged per slot with `log_slot_specific_purchase`. It lifts only the per-element cap (3 or 5 -> 15). The element-count limit still applies. Whether a slot is overclocked is stored nowhere else: `RunLedgerComponent.is_overclocked(slot)` is true when the slot-specific purchase of an `ABILITY_OVERCLOCK` card is above 0, and `EvolutionGateComponent.is_permanently_overclocked` is a read-only answer from the ledger (wired by `configure_slot_context(slot, ledger)`, like the infusion tracker). A plain (non-slot) purchase overclocks nothing.
- Compounds (Fire + Lightning = Plasma) have no infusion level and no tag yet. The first compound effect is a stat on the evolved profile: `CRIT_DOT_SHARE` (Task R) makes a crit cast multiply that cast's Burn snapshot by `1 + (CRIT_MULTIPLIER - 1) * CRIT_DOT_SHARE`. Only an evolved profile sets it. A `PLASMA` tag and a shared card are added only when a card needs to target Plasma abilities.

## Combat design decisions
- Two separate damage channels. **Hit** uses `BASE_DAMAGE`, crit chance and crit multiplier. **DoT** uses its own `DOT_DAMAGE` and `STATUS_DURATION`. DoT never reads `BASE_DAMAGE`, and DoT ticks never crit.
- Fire is the DoT element (duration theme). Lightning is the hit element (crit theme).
- **Two stats on every ability.** Every ability profile carries a nonzero `BASE_DAMAGE` and a nonzero `DOT_DAMAGE`. `DOT_DAMAGE` is inert potency: nothing ticks until a status with a duration is applied. There is no cast-time duration gate. `StatusEffectComponent.apply_effect` returns early when the effective duration (template `base_duration` plus the `STATUS_DURATION` bonus) is 0 or less, so there is no instance, no tag, no ticks and no warning.
- **Fire deals no damage itself.** Per level it adds flat `STATUS_DURATION` (+3.0 s) and flat `STATUS_RAMP_CAP` (+0.1). Flat modifiers scale as `value * tier`. The cap bonus flows through `status_ramp_cap_snapshot` to `StatusEffectInstance.ramp_cap_bonus`, the same path as `duration_bonus`, and a refresh takes the latest applier's value. Burn's template `base_duration` is 0, so duration comes only from Fire. A card carries all its stat modifiers in one ordered list, UpgradeDefinition.stat_modifiers (Fire has two). All numbers are placeholders.
- **Indirect infusion scalings** unlock by infusion level and boost both channels through a cast-time `damage_scale` applied to final hit damage and `dot_damage_snapshot` (indirect bonuses summed, then capped; cap undecided). Frost: bonus per 0.1 s shaved off the default cooldown (level 2). Wind: speed ratio, with one generic speed stat read by every driver (level 2). Lightning (overload on crit, level 3) and Earth (on-impact explosion scaling with enemies caught, level 3) share the impact-burst mechanism (see Architecture rules). Burst effects scale off hit damage.
- Area abilities read `AOE_RADIUS` for their reach, and projectile and orbit hitboxes read it too. Chain link keeps `QUERY_RADIUS` / `CHAIN_RADIUS`, and projectile targeting keeps `QUERY_RADIUS`.
- Infusions contribute through stat modifiers (UpgradeDefinition.stat_modifiers) and, optionally, a status carried by the card (`status_effect_payload`). Effect templates define shape only (tick interval, ramp, stacking), never absolute damage.
- Card scaling is multiplicative, per card: the ledger multiplies `pow(1.0 + value, tier)` for each card, where tier is the card's duplicate count. Final stat = `(base + flat) * (1 + percent) * multiplicative`. This was the one rule that made both specializations viable in the balance workbook.
- **Stacking (Decided Oct 18; Task P builds the mechanism, no card uses it yet).** REFRESH is a stack cap of 1. A ticking status's cap is its template cap (1 for REFRESH templates, `max_stacks` for STACK templates) plus the `STATUS_STACK_BONUS` stat, snapshotted at cast time like `STATUS_DURATION` and `STATUS_RAMP_CAP`; non-ticking statuses (Chill) ignore it. Templates never change and there are no Burn variants. Burn's template stays REFRESH with `max_stacks` 1, so nothing stacks until a card raises the stat. All stacks share one timer and expire together; a re-apply takes the latest applier's snapshot, keeps `elapsed` and never lowers the stack count. Tick damage is `dot_damage * ramp * interval * stacks`. Fire stays build agnostic: it supplies duration and ramp cap only and never carries a stack bonus, so duration builds and stacking builds are the player's choice. How stack cards are introduced is undecided (GDD item 44).
- Status effect templates are never mutated. Runtime state lives in `StatusEffectInstance`. Statuses are not persisted between rooms. Burn ramp is +10%/s capped at +50%, matching the workbook. All other Burn and Chill numbers are placeholders.
- All numbers in the balance workbook are placeholders.
- **Status application rules.** Any `UpgradeDefinition` can carry a `status_effect_payload`, resolved through the ledger with the normal scope rules and deduplicated by `effect_id`. Statuses are chosen at cast time and applied on every hit (no chance stat). A ticking status is skipped when the ability's `DOT_DAMAGE` snapshot is 0. `STATUS_DURATION` is ability-wide. A status whose effective duration is 0 or less is not applied at all. No status variants.

- Be careful with `.tscn` / `.tres` edits: they hold resource IDs and enum integers. Keep diffs small and review them.
- Prefer editing existing files over creating new ones. Do not add features that were not asked for.
- Debug tools live in `res://debug/` behind one panel (`DebugHub`, F1, debug builds only). Put the logic of a new debug action in `DebugActions` as a static function with a logic check, and add its button to the panel. Do not add other hotkeys or separate debug nodes to scenes.
- Do not claim something works unless it was actually run, and say which kind of run it was (Verified or Headless).
- Headless checks (Godot 4.5; `$GODOT` is `C:\Users\chris\Desktop\Godot_v4.5-stable_win64.exe`; run from the project root):

  - World run (600 frames, read the errors; about 4 s): `$GODOT --headless --path . res://scenes/world/world.tscn --quit-after 600`

    - Scripts in `tools/headless/`: `runner.gd` (runs a check script), `logic_test.gd` (behavior checks), `golden_test.gd` (characterization checks), `fixtures.gd` (clean state per section), `load_all.gd` (load check), plus the `golden/` folder holding `golden_values.json`.
